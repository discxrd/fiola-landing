# AGENTS.md — инструкции для разработки Fiola landing

Этот файл — рабочий контракт для всех AI-агентов и разработчиков, которые продолжают статический лендинг Fiola. Проект собирается по блокам из Figma, на русском языке, с приоритетом точной верстки, доступности, SEO и Lighthouse 100.

## Главная цель

- Делать статический лендинг на HTML + CSS + минимальный JS без фреймворков.
- Добавлять каждый экран из Figma отдельным, изолированным блоком.
- Держать проект быстрым, доступным, SEO-ready и безопасным для дальнейших GSAP-анимаций.
- Не ухудшать уже созданную структуру, БЭМ, производительность и валидацию.

## Источники правды

1. Figma-макет или скрин блока — источник визуальной правды.
2. `index.html` — источник структуры страницы.
3. `styles/main.css` — единый runtime CSS-файл.
4. `scripts/main.js` — единая точка входа для будущих JS/GSAP-сценариев.
5. `README.md` — пользовательская документация по проекту.
6. `AGENTS.md` — обязательные инструкции для AI-агентов.

Если README и AGENTS конфликтуют, для реализации следуй `AGENTS.md`, но не ломай публичную документацию в `README.md`.

## Строго по дизайну Figma

- НИКАКИХ ВЫДУМЫВАНИЙ: не добавляй тексты, декоративные элементы, цвета, эффекты, отступы, анимации или композиционные решения, которых нет в Figma-макете или явно приложенном скрине.
- Работа ведётся только по дизайну из Figma/скрина. Если Figma MCP недоступен, остановись на этапе визуальной реализации и сообщи, что без доступа к макету нельзя точно сверстать блок.
- Если в Figma выделено несколько фреймов как один сценарий/секция, сохраняй их последовательность, размеры, визуальные состояния и скролл-логику без самостоятельной интерпретации.
- Допускаются только технические адаптации, необходимые для HTML/CSS, доступности и responsive, если они не меняют визуальный смысл и явно основаны на макете.

## Рабочий процесс для каждого нового блока

1. Сначала изучи текущие `index.html`, `styles/main.css`, `scripts/main.js` и релевантные ассеты.
2. Если пользователь прислал экспорт Anima (`index.html`, `globals.css`, `style.css`) — используй его как визуальную спецификацию, а не как готовую архитектуру.
3. Если дан Figma node/file id — используй доступные Figma-инструменты, токены, размеры, цвета и текст из макета.
4. Если дан только скрин — воспроизведи блок максимально близко, явно фиксируя разумные допущения в финальном ответе.
5. Добавь блок в `main` как отдельный `section` с уникальным `data-block="block-name"`, кроме повторных шапок из экспорта.
6. У каждой секции должен быть связанный заголовок через `aria-labelledby`.
7. Сохраняй корректную иерархию заголовков: один `h1` на странице, дальше `h2`/`h3` без логических скачков.
8. После реализации проверь адаптив минимум на desktop и mobile-ширине, указанной в макете или в задаче.
9. Всегда запускай `npm run check` после изменений. Если менялся JS — дополнительно `node --check ./scripts/main.js`.

## Работа с экспортом Anima

- Не копируй классы Anima в production (`.HERO`, `.frame`, `.div`, `.text-wrapper`, `.group`, `.img`) без переименования по БЭМ.
- Переводи структуру Anima в семантическую HTML-разметку проекта: `section`, `header`, `nav`, `a`, `button`, `picture/img`, списки и заголовки.
- `globals.css` и `style.css` из Anima используй как источник размеров, цветов, шрифтов, отступов, теней и эффектов.
- Если DevTools-копия содержит мусор (`<pre>`, syntax-highlight span/class, inline-подсветку кода, дубли wrapper-ов), полностью очищай его и переноси только смысловую структуру, текст, размеры и визуальные параметры.
- Если блок содержит повторный `header`/`nav`, не добавляй его в разметку блока: на странице должен быть один глобальный sticky/fixed header, а повторный header из экспорта служит только подсказкой для активного пункта и состояния навигации.
- Не переноси `@import` reset из Anima и не подключай отдельные `globals.css`/`style.css`; все runtime-стили должны попасть в `styles/main.css`.
- Абсолютные desktop-размеры из Anima адаптируй через `max-width`, `clamp()`, `min()`, `max()` и media queries, чтобы блок не ломал mobile.
- Если Anima использует локальные restricted fonts, задай безопасные fallback-цепочки и не подключай внешние шрифты без явной необходимости.
- Перед финальным ответом проверь, что новая разметка проходит проектный БЭМ-чекер.

## HTML и декомпозиция

- Используй семантические теги: `header`, `main`, `section`, `nav`, `ul/ol`, `article`, `footer`, `button`, `a`.
- Не делай div-суп без необходимости.
- Каждый Figma-экран — отдельный блок верхнего уровня.
- Внутренние смысловые группы оформляй элементами блока по БЭМ.
- Для декоративных элементов не добавляй лишний текст в DOM; используй CSS-псевдоэлементы, когда это проще и доступнее.
- Все интерактивные элементы должны быть доступны с клавиатуры и иметь видимый `:focus-visible`.
- Русский текст сохраняй в разметке, не выноси статический контент в JS.

## БЭМ и CSS-архитектура

- Все классы должны соответствовать БЭМ: `block`, `block__element`, `block--modifier`, `block__element--modifier`.
- Новый блок получает собственный префикс класса, совпадающий по смыслу с `data-block`.
- Стили блока добавляй в `styles/main.css` внутри `@layer blocks`.
- Переиспользуемые элементы добавляй в `@layer components`.
- Сетки, контейнеры и общие layout-решения добавляй в `@layer layout`.
- Токены цветов, радиусов, теней, отступов и типографики добавляй в `@layer settings` через CSS custom properties.
- Не используй каскад между независимыми блоками вроде `.block-a .block-b`.
- Не используй CSS `@import`.
- Используй `clamp()`, logical properties, CSS variables и cascade layers, но избегай экспериментальных API без стабильной поддержки.
- Для нестандартных современных возможностей добавляй безопасный fallback, если это влияет на актуальные Chrome/Safari/Firefox/Edge.

## Адаптив и визуальная точность

- Верстай от макета, а не от догадки: размеры, отступы, цвета, радиусы, тени и композицию сверяй с Figma/скрином.
- Desktop должен совпадать с шириной фрейма из задачи; mobile — с мобильным фреймом, если он есть.
- Если промежуточные брейкпоинты не заданы, делай плавный responsive через `clamp()`, `min()`, `max()`, flex/grid.
- Не добавляй визуальные эффекты, которых нет в макете, если пользователь не просит улучшить дизайн.
- Допустимы аккуратные технические улучшения, которые не меняют визуальный смысл: сглаживание адаптива, доступные состояния фокуса, оптимизация загрузки.

## Ассеты, изображения и SVG

- Все пользовательские ассеты клади в `assets/`.
- Если для блока не хватает ассетов из Anima/Figma, попроси пользователя прислать только нужные файлы и перечисли их исходные имена.
- После получения ассетов переименовывай файлы в человекочитаемые SEO-friendly имена латиницей через kebab-case: например, `group-1.svg` → `fiola-hero-orbital-background.svg`, `vector-1.svg` → `fiola-nav-active-divider.svg`.
- После переименования обновляй все ссылки в HTML/CSS и не оставляй технические имена Anima вроде `group-1`, `vector-2`, `image-123`.
- Подключай изображения с `width`, `height`, `alt`, `decoding="async"`.
- Для первого видимого hero-изображения используй `fetchpriority="high"`, для остальных обычно `loading="lazy"`.
- Содержательные изображения получают уникальный осмысленный `alt`; декоративные — `alt=""`.
- Статичные SVG храни в `assets/`.
- Inline SVG используй только когда нужно управлять цветом, состояниями, масками или анимацией из CSS/JS.
- Не подключай тяжелые изображения без оптимизации размеров и формата.

## JS и GSAP

- По умолчанию решай задачу HTML/CSS. JS добавляй только для реального поведения или анимаций.
- Весь runtime JS держи в `scripts/main.js` или явно обоснованных дополнительных файлах в `scripts/`.
- Все внешние скрипты должны быть `defer` или `type="module"`.
- GSAP подключай только когда есть конкретная анимационная задача.
- Любая GSAP-инициализация должна проверять `window.gsap` и уважать `prefers-reduced-motion: reduce`.
- Страница должна выглядеть корректно без JS; JS может улучшать, но не должен быть обязательным для чтения контента.
- Не блокируй critical path скриптами, анимациями или тяжелыми библиотеками.

## SEO, доступность и Lighthouse

- Сохраняй один `h1` на странице.
- Поддерживай `title`, `meta description`, canonical, Open Graph, Twitter meta и JSON-LD в актуальном состоянии перед релизом.
- Не ухудшай keyboard navigation, контраст, читаемость и фокусные состояния.
- Не добавляй layout shift: задавай размеры медиа и избегай поздней вставки контента над fold.
- Не подключай лишние шрифты, библиотеки и трекеры.
- Critical CSS уже находится в одном `styles/main.css`; не дроби CSS без необходимости.
- Уважай `prefers-reduced-motion` для CSS- и JS-анимаций.

## Запрещено

- Ломать БЭМ-нейминг или добавлять utility-классы без явной причины.
- Использовать CSS `@import`.
- Добавлять фреймворки, сборщики или зависимости без необходимости.
- Переносить статический контент в JS.
- Удалять проверки или ослаблять `scripts/quality-check.js`, чтобы скрыть проблему.
- Удалять существующую доступность: skip-link, `aria-labelledby`, alt-тексты, focus states.
- Коммитить изменения без явной просьбы пользователя.

## Обязательная проверка перед финальным ответом

Минимум после каждого изменения:

```bash
npm run check
```

Дополнительно при изменении JS:

```bash
node --check ./scripts/main.js
```

Если менялся `scripts/quality-check.js`, проверь и его:

```bash
node --check ./scripts/quality-check.js
```

В финальном ответе кратко укажи:

- какие файлы изменены;
- что именно добавлено или исправлено;
- какие проверки запущены и их результат;
- какие допущения были сделаны, если макет/ассеты были неполными.
